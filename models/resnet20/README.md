# ResNet-20 (CIFAR-10) on tt-foil

End-to-end ResNet-20 inference on a single Tensix core (Blackhole, slow-dispatch).
Loads the pretrained akamaster checkpoint, folds BatchNorm into the preceding Conv,
runs the full forward pass on device, and compares logits against a pre-computed
reference.

Reference (akamaster, option-A skip): https://github.com/akamaster/pytorch_resnet_cifar10

## Performance at a glance

| Stage | Wall (1-image inference) | vs baseline |
|---|---:|---:|
| Baseline (host im2col + read-back per op) | 166.9 ms | 1.00× |
| Tier 1.1 — DevBuf threading | 117.7 ms | 1.42× |
| Tier 2.2 — pin `bias_relu_post` | 114.7 ms | 1.46× |
| Tier 1.2 — fuse ReLU into `residual_add` | **111.0 ms** | **1.50×** |

Chip utilisation rose from 7.4 % (baseline) to ~11 % — wall is still
PCIe / host bound by `host_im2col_3x3` + the activation-input read
before each conv. See [`PERF_HISTORY.md`](PERF_HISTORY.md) for the
full iteration log (including the Step 4 fast-dispatch deferral and the
Step 2 device-im2col regression) and [`PERFORMANCE.md`](PERFORMANCE.md)
for the original bottleneck analysis.

Correctness across all iterations: `argmax dev = 3 (cat) = ref`,
`worst_abs = 0.1367` (bf16 truncation only).

## Prerequisites

- tt-metal source tree (the submodule at `third_party/tt-metal`) built once via
  `./build_metal.sh --release`. See the top-level `CLAUDE.md` for full details.
- Python venv with `torch` + `torchvision` for `export.py`. The repo's
  `~/tt-venv` works.
- A Blackhole chip; pick its PCIe index with `TT_FOIL_DEVICE`.

## Running the test

```bash
# 1. (one-time) Configure + build tt-foil with HW tests on
TT_METAL_BUILD_DIR=$PWD/third_party/tt-metal/build_Release \
    cmake -B build -DTT_FOIL_HW_TESTS=ON -DTT_FOIL_DEVICE=0
cmake --build build -j$(nproc)
# This auto-builds: tt-foil's own firmware → resnet20 kernel set →
# data/resnet20/{weights,image,golden,manifest}.* via export.py.

# 2. Reset the chip (only needed if a previous run crashed it)
$HOME/tt-venv/bin/tt-smi -r 0

# 3. Run via ctest (preferred — sets TT_FOIL_KERNEL_DIR / TT_FOIL_DATA_DIR
#    for you, and serialises against other HW tests on the chip):
ctest --test-dir build -R test_resnet20 --output-on-failure

# 3b. Or invoke the binary directly:
TT_FOIL_DEVICE=0 \
TT_FOIL_KERNEL_DIR=$PWD/models/resnet20/prebuilt \
TT_FOIL_DATA_DIR=$PWD/data/resnet20 \
./build/tests/test_resnet20
```

## Per-stage golden check

To verify each conv / block boundary against a host PyTorch reference:

```bash
TT_FOIL_DEBUG_STAGES=1 \
TT_FOIL_DEVICE=0 \
TT_FOIL_KERNEL_DIR=$PWD/models/resnet20/prebuilt \
TT_FOIL_DATA_DIR=$PWD/data/resnet20 \
./build/tests/test_resnet20
```

Per-stage `*.bin` reference tensors live under `data/resnet20/stages/`
(re-generated by `export.py`). Diffs are reported as
`(C=… HxW) worst abs=… at idx … (dev=… ref=…)`.

## Re-exporting the data

The C++ test reads `data/resnet20/weights.bin` + `image.bin` + `golden.bin`
+ `manifest.txt`, all produced by `export.py`. The CMake target
`resnet20_data` regenerates these if the script changes, but you can
also invoke it manually:

```bash
python3 models/resnet20/export.py --out-dir $PWD/data/resnet20
# Optional flags:
#   --image-index N    pick CIFAR-10 test image N (default 0, label = cat)
#   --cache-dir DIR    where to stash the checkpoint + CIFAR-10 download
```

First run downloads the akamaster checkpoint (~1 MB) and the CIFAR-10
test set (~170 MB) into `.cache/`.

## Re-building the kernel set

Triggered automatically by `cmake --build build`, but to force a clean
rebuild (e.g. after editing a kernel `.cpp`):

```bash
rm -rf models/resnet20/prebuilt examples/{conv_3x3,conv_3x3_s2,residual_add}/prebuilt
rm -f build/resnet20_kernels.stamp
cmake --build build -j$(nproc) --target test_resnet20
```

The build script is [`build_kernels.sh`](build_kernels.sh) — it
parameterises `examples/conv_3x3*`, `examples/residual_add`, and
`examples/conv_1x1` to produce the 11 shape-specific variants ResNet-20
needs.

## Architecture (akamaster, option-A skip)

```
stem      conv 3×3 s=1 (3→16)  + bias + ReLU                → (16, 32, 32)
layer1.k  conv 3×3 s=1 (16→16) + bias + ReLU
          conv 3×3 s=1 (16→16) + bias
          skip = identity
          ReLU                                                → (16, 32, 32)
layer2.0  conv 3×3 s=2 (16→32) + bias + ReLU                  ← downsample
          conv 3×3 s=1 (32→32) + bias
          skip = subsample-stride-2 then zero-pad channels    → (32, 16, 16)
          ReLU
layer2.{1,2}: basic block at (32, 16, 16) like layer1
layer3.0:    downsample like layer2.0 but (32→64, 16→8)
layer3.{1,2}: basic block at (64, 8, 8)
GAP                                                            → (64,)
FC: (10, 64)                                                   → 10 logits
```

Channel padding: every channel-count gets rounded up to 32 (tt-foil's
tile width), so C=3 (RGB) and C=16 layers are stored as C=32 with the
extra channels zeroed. The conv kernels multiply zero × weight for the
padded slots — wasteful in FLOPs but correct.

Option-A skip math is computed on the host (zero-padded subsample), so
no 1×1 conv kernel is needed for the layer2.0 / layer3.0 downsample.

## Known limitations / future work

- `host_im2col_3x3` (~20 ms) and `host_tile_matrix` (~30 ms) still
  dominate the remaining wall — a viable device-side im2col + a
  smarter host packing layer would unlock most of the remaining
  headroom. See `PERF_HISTORY.md` Step 2 for what was tried and why it
  regressed.
- Single Tensix core only; the chip has ~140 of them. A multi-core
  split (along `Mt` and/or `Nt`) is the obvious next axis.
- bf16 throughout. No quantisation / accuracy comparison vs fp32.
- One image at a time. The bump allocator and dispatch flow assume
  N = 1; batching needs allocator work.
